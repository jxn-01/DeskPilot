DeskPilot.

A service-desk assistant that prepares evidence-backed ticket triage for an analyst to review. It suggests a category, urgency, and next step; the human remains responsible for every decision.

Main guide

Use DeskPilot

The app opens with six synthetic tickets. For a broader test, download the ten-ticket alternate set and upload it in the app.

01

Open the demo

Visit the live app. The sidebar shows whether the app is in offline demo mode or connected to an LLM.

No setup is needed to try the built-in examples.
02

Load a ticket file

Keep the built-in six tickets, or use the uploader to select a CSV with ticket_id and description columns. The alternate file explores BI, facilities, expenses, and access scenarios.

Download 10 alternate tickets
03

Optionally add support guides

Upload Markdown or text files with sections beginning with ##. Otherwise, DeskPilot uses its included synthetic support guides.

View included guide
04

Analyze, inspect, and export

Choose Analyze tickets. Review the queue summary, select a ticket, inspect the suggested next step and guide evidence, then download the review as CSV.

A human analyst makes the final decision.
Category

Connectivity, account access, software, security, or other.

Urgency and review

Security signals are high urgency; security, access grants, software approvals, uncertainty, and missing evidence are flagged for human review.

Suggested next step

A recommendation with the matched guide title and its supporting excerpt when available.

Demo safety: Use synthetic data only. DeskPilot does not send replies, change permissions, unlock accounts, install software, or close tickets. In live LLM mode, ticket text and retrieved guide excerpts are sent to the configured model endpoint.

Annex B / Rebuild with AI tools

Reproducibility

Build a similar tool from scratch

Use GitHub Copilot as a pair-programmer: ask for small, testable changes, inspect the code, run it, and verify the outputs. AI-generated code still needs human review.

  1. Turn the brief into a contract

    Write down the user, input format, expected output fields, safety rules, and what the prototype will not do. Agree on sample cases before writing code.

  2. Ask Copilot for a minimal scaffold

    Start with a Streamlit page, requirements file, and synthetic CSV. Keep the initial scope to one workflow and one screen.

    Build a small Streamlit prototype for synthetic support tickets.
Input CSV columns: ticket_id, description.
Show category, urgency, suggested action, guide evidence,
and needs_human_review. Never perform ticket actions.

  3. Implement one step at a time

    Ask for CSV validation, guide loading, retrieval, and classification separately. Review each diff and run the app after each change.

  4. Make safety explicit

    Keep security escalation and human approval rules in code. Ask Copilot to add tests for credential exposure, software approval, missing evidence, malformed CSV, and model failure.

  5. Add live LLM use only after offline tests pass

    Store keys in the hosting provider's secrets manager. Use structured output, validate model fields, show evidence, and keep deterministic safety overrides.

  6. Test against a separate answer key

    Compare category, urgency, and review flags to expected results. Keep the answer key out of the app's input flow; manually inspect the evidence and failure cases.

  7. Publish and verify

    Push only intended files to GitHub, deploy the app, set secrets through Cloud settings, and test the deployed URL with synthetic data.

Useful Copilot habit: ask it to explain a proposed change and name the test that would prove it works. Don’t paste passwords, API keys, customer tickets, or confidential documents into prompts.
Annex C / Recommended addition

Event-day adaptation

A playbook for the 2 PM brief

This is the extra section I recommend: it turns the prototype into a reusable team method for an unknown case, without pretending DeskPilot is the answer to every business problem.

Understand the case

Who has the problem? What work is slow, risky, costly, or inconsistent? What outcome matters?

Shape a measurable pilot

Choose one narrow workflow, a demo input, one success measure, and a baseline the team can explain.

Map AI to the work

Use retrieval when trusted knowledge matters; use classification for routing; use an agentic sequence only when multiple steps genuinely add value.

Check risk and control

Identify sensitive data, unsupported claims, approval points, and what the prototype must never do automatically.

Build the smallest demo

Change the input, guidance, and output around the case. Avoid new infrastructure unless the story needs it.

Present evidence

Show one realistic case, its evidence, a human decision, one measured result, limitations, and the next pilot step.

Suggested five-person split

BI owns measures and the value case; cybersecurity reviews data and safeguards; project management keeps scope and time; one teammate handles the demo and tests; one coordinates the problem framing and pitch. Rotate roles to match the actual brief.
